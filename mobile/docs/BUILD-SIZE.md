# Release build size and hardening

Everything here is configured through the `expo-build-properties` plugin block in
`mobile/app.json`. Nothing is configured by editing `android/` — that directory is
generated by `expo prebuild` and gitignored, so a hand edit survives exactly until
the next prebuild and then vanishes silently.

---

## 1. Measured baseline

Measured on `mobile/android/app/build/outputs/apk/release/app-release.apk`, which
DELIVERY.md records as byte-identical to the shipped EAS artifact
(`094170f0`). Sizes are **compressed**, i.e. bytes as they sit in the APK.

```
APK on disk: 132.8 MB (139,302,059 bytes)
```

| Section | Compressed | Share |
|---|---:|---:|
| `lib/x86` | 29.55 MB | 22.3% |
| `lib/x86_64` | 28.79 MB | 21.7% |
| `lib/arm64-v8a` | 27.25 MB | 20.5% |
| `lib/armeabi-v7a` | 18.68 MB | 14.1% |
| **`lib/` total** | **104.27 MB** | **78%** |
| `classes*.dex` | 19.82 MB | 14.9% |
| `assets/` (Hermes bundle + fonts) | 4.24 MB | 3.2% |
| `resources.arsc` | 2.18 MB | 1.6% |
| `res/` | 1.08 MB | 0.8% |
| everything else | ~0.17 MB | 0.1% |

The shape of the problem: **78% of this APK is native code, and 44% of it is
native code for CPUs that no Android phone has.**

Reproduce with:

```bash
python - <<'PY'
import zipfile, collections, os
p = "android/app/build/outputs/apk/release/app-release.apk"
z = zipfile.ZipFile(p); abi = collections.Counter()
for i in z.infolist():
    if i.filename.startswith("lib/"):
        abi[i.filename.split("/")[1]] += i.compress_size
print("APK %.1f MB" % (os.path.getsize(p)/1048576))
for k, v in abi.most_common(): print("  %-12s %6.2f MB" % (k, v/1048576))
PY
```

## 3. The settings, and what each one actually does

```jsonc
["expo-build-properties", { "android": {
  "minSdkVersion": 26,
  "buildArchs": ["arm64-v8a", "armeabi-v7a"],
  "enableMinifyInReleaseBuilds": true,
  "enableShrinkResourcesInReleaseBuilds": true,
  "extraProguardRules": "..."
}}]
```

### `buildArchs: ["arm64-v8a", "armeabi-v7a"]` — the 58 MB

The plugin writes this to `android/gradle.properties` as
`reactNativeArchitectures` (`expo-build-properties/src/android.ts:114`), replacing
the default `armeabi-v7a,arm64-v8a,x86,x86_64`.

That property is not advisory. The React Native Gradle plugin reads it in
`NdkConfiguratorUtils.configureReactNativeNdk` and does:

```kotlin
val architectures = project.getReactNativeArchitectures()
if (architectures.isNotEmpty() && !ext.splits.abi.isEnable) {
  ext.defaultConfig.ndk.abiFilters.addAll(architectures)
}
```

`configureReactNativeNdk` is called unconditionally from `ReactPlugin.kt:83`.
This matters: `ndk.abiFilters` is an **AGP-level packaging filter**, so it also
strips `.so` files that arrive inside prebuilt dependency AARs (ReactAndroid,
hermes-engine, every Expo module with native code). If it only affected code
compiled from source it would save almost nothing here, because this app does not
build React Native from source.

The guard `!ext.splits.abi.isEnable` is satisfied — `android/app/build.gradle`
declares no `splits` block.

### `enableMinifyInReleaseBuilds: true` — R8

`android/app/build.gradle:69` reads `android.enableMinifyInReleaseBuilds` into
`minifyEnabled` for the release build type. R8 then shrinks, optimises and
obfuscates the 19.8 MB of dex. Rules come from
`getDefaultProguardFile("proguard-android.txt")` plus `app/proguard-rules.pro`,
which is where `extraProguardRules` is appended.

### `enableShrinkResourcesInReleaseBuilds: true`

`android/app/build.gradle:117` → `shrinkResources`. Removes resources no code
path references. AGP requires `minifyEnabled` alongside it, and the plugin
enforces the same pairing before prebuild — configuring shrink without minify
throws:

> `android.enableShrinkResourcesInReleaseBuilds` requires
> `android.enableMinifyInReleaseBuilds` to be enabled.

Safe for Tier-0, checked rather than assumed: the foreground-service notification
icon is referenced as `R.drawable.kavach_t0_status`
(`KavachForegroundService.kt:276`) and the device-admin policy as
`@xml/kavach_device_admin` from the module manifest — both are traceable roots.
There is **no `Resources.getIdentifier()` call anywhere in `modules/` or
`plugins/`**, which is the one pattern the resource shrinker cannot follow.

### `minSdkVersion: 26` — unchanged

Direct Boot (`createDeviceProtectedStorageContext`), `AdvertisingSetCallback` and
vector notification icons all land at API 26. Not a size lever; listed so nobody
"tidies" it away.

## 4. Two key names that do not exist in SDK 57

Worth recording, because both fail *quietly*.

**`abiFilters` is not a key.** The `android` object in the plugin's JSON schema
(`expo-build-properties/src/pluginConfig.ts:650-784`) does **not** set
`additionalProperties: false`, so an unknown key is accepted without warning and
then ignored. Verified directly against the installed validator:

```
validateConfig({ android: { abiFilters: [...] } })
  -> accepted, no error
  -> android.buildArchs is undefined
```

The build would have completed green and stayed 132 MB. The correct key is
`buildArchs`.

**`enableProguardInReleaseBuilds` is deprecated.** It still works, but only via a
shim (`fixupDeprecatedEnableProguardInReleaseBuilds`, `pluginConfig.ts:888`) that
copies it onto `enableMinifyInReleaseBuilds` before validation. `build.gradle`
itself only ever reads `android.enableMinifyInReleaseBuilds`. Use the real name.

## 5. The ProGuard keep rules

R8 runs on release builds only. Anything it strips is missing from the one build
users install, and for Tier-0 that failure is **silent** — the OS does not raise
an error when it fails to deliver `LOCKED_BOOT_COMPLETED` to a class that is no
longer there. The emergency plane would simply not exist, with no crash, no log a
user would see, and nothing a smoke test would catch. Each rule below buys
certainty for a few KB of dex.

The rules live in `app.json` under `extraProguardRules`, with these same
justifications inline as `#` comments, and the plugin appends them to
`android/app/proguard-rules.pro` on every prebuild.

### `-keep class expo.modules.kavacht0.** { *; }`

`modules/kavach-t0/android/build.gradle` ships **no `consumerProguardFiles`** —
deliberately, and unlike `expo-modules-core`, `expo-notifications`,
`expo-location`, `expo-task-manager` and `expo-background-task`, all of which ship
their own. So the T0 classes arrive at R8 with zero rules of their own.

The four components named in the module's `AndroidManifest.xml`
(`KavachForegroundService`, `BootReceiver`, `ShutdownReceiver`,
`KavachDeviceAdminReceiver`) *are* keep roots via the merged manifest — but a
manifest root keeps the **class**, not necessarily its members. And
`KavachT0Module` is not in the manifest at all: it is reached only through the
generated `ExpoModulesPackageList`, listed by name in `expo-module.config.json`.
`expo-modules-core`'s own rule for module classes is
`-keep,allowoptimization,allowobfuscation ...`, i.e. it explicitly permits
renaming. Keeping the whole package removes every one of these edge cases at
once, for a package of seven Kotlin files.

### `-keep class * extends expo.modules.kotlin.records.Record { *; }`

Records are populated entirely by reflection. `RecordTypeConverter` locates
`@Field` with `kotlin.reflect`'s `findAnnotation()`, then writes each value with
`javaField.set(instance, casted)` — **keyed on the Kotlin property name**
(`RecordTypeConverter.kt:63-103`).

A renamed field does not throw. `jsMap.hasKey(jsKey)` returns false, the branch
returns early, and the property keeps its default. For `ForegroundAgentOptions`
that silently discards the entire P-035 pre-unlock provisioning payload —
`emergencyNumbers`, `peerFingerprints`, `guardianReleaseTokenSha256`,
`policySnapshotJson` — leaving T0 running, reporting healthy, and configured with
nothing.

`expo-modules-core` ships the `implements` twin of this rule (`implements` and
`extends` are equivalent in ProGuard/R8 grammar). Keeping our own copy means a
dependency bump that drops or narrows that consumer rule cannot take the
emergency plane with it.

### `-keepattributes RuntimeVisibleAnnotations,AnnotationDefault,Signature,InnerClasses,EnclosingMethod`

The reflection above needs the metadata that carries it:

- `@Field` is `@Retention(AnnotationRetention.RUNTIME)` — `findAnnotation()` only
  sees it if `RuntimeVisibleAnnotations` survives.
- `Signature` preserves generic types. `ForegroundAgentOptions` has
  `emergencyNumbers: List<String>?` and `peerFingerprints: List<String>?`; strip
  `Signature` and `property.returnType` resolves to a raw `List` with no element
  type, so the converter cannot pick an element converter.
- R8 **full mode is the AGP 8 default** and `android/gradle.properties` does not
  set `android.enableR8.fullMode`, so nothing here should be assumed inherited.

### `-keep class kotlin.Metadata { *; }`

`kotlin-reflect` is on the classpath (`expo-modules-core/android/build.gradle:210`)
and `memberProperties` resolves through the `@kotlin.Metadata` annotation. Zero
size cost; removes a whole class of silent Record failure.

## 6. What dropping x86 costs

**Nothing on real hardware.** No shipping Android phone or tablet uses an x86 or
x86_64 CPU. Both ABIs exist in the default list for emulators.

**It costs emulator testing.** After this change:

- The standard Android Studio AVDs — which are x86_64 on Intel/AMD hosts — will
  **not** install this APK. `adb install` fails with `INSTALL_FAILED_NO_MATCHING_ABIS`.
- Apple Silicon Macs are unaffected: those AVDs are `arm64-v8a`.
- CI or contributors on x86_64 Linux/Windows who test on an emulator need an
  **arm64-v8a AVD**, which runs under full emulation and is slow.

Both workarounds keep `app.json` untouched:

```bash
# One-off local emulator build — Gradle property beats gradle.properties
cd mobile/android && ./gradlew assembleRelease -PreactNativeArchitectures=x86_64

# Or test the debug variant, which is unaffected by minify/shrink anyway
cd mobile/android && ./gradlew assembleDebug -PreactNativeArchitectures=x86_64
```

This trade is right for Kavach specifically: Tier-0 is a foreground service, a
Direct Boot receiver, a shutdown broadcast and multi-SIM `SmsManager`. None of it
is meaningfully testable on an emulator regardless of ABI, so the emulator was
never the verification path for the part of the app that matters.

Note this only trims what the **APK** carries. The `production` EAS profile
builds an AAB (`eas.json`), where Play generates per-device splits and each user
already downloads one ABI. `buildArchs` still helps there by shrinking the
uploaded bundle and its build time.

## 7. Verifying the next build did not strip Tier-0

Minification is the risk this document exists for, so check the artifact rather
than trusting the config. Baseline from the current unminified APK: **75 types**
under `expo/modules/kavacht0/`.

```bash
cd mobile && python - <<'PY'
import zipfile
p = "android/app/build/outputs/apk/release/app-release.apk"   # or the EAS download
z = zipfile.ZipFile(p)
dex = b"".join(z.read(n) for n in z.namelist() if n.endswith(".dex"))
classes = ["KavachForegroundService", "BootReceiver", "ShutdownReceiver",
           "KavachDeviceAdminReceiver", "KavachT0Module", "ForegroundAgentOptions",
           "T0Config", "T0Sms", "DeviceOwnerConfigurator"]
fields  = ["emergencyNumbers", "peerFingerprints", "guardianReleaseTokenSha256",
           "policySnapshotJson", "preferredSubscriptionId", "incidentActive"]
miss_c = [c for c in classes if c.encode() not in dex]
miss_f = [f for f in fields  if f.encode() not in dex]
print("classes:", miss_c or "all present")
print("record fields:", miss_f or "all present")
print("ABIs:", sorted({n.split('/')[1] for n in z.namelist() if n.startswith('lib/')}))
PY
```

Expected after the hardened build:

- `classes: all present` — proves `-keep class expo.modules.kavacht0.**` held.
- `record fields: all present` — the Record property names were **not** renamed.
  This is the one that fails silently at runtime if the keep rules are wrong, so
  it is the one worth checking.
- `ABIs: ['arm64-v8a', 'armeabi-v7a']` — proves `buildArchs` was honoured and not
  silently ignored.

If the field-name check fails, the APK will still install, launch and pass a
manual SOS test in the foreground. It will fail only at pre-unlock provisioning,
on a locked phone, during an emergency. Do not ship on a green install alone.
