# ADR-009 — Relationship-based authorization (ReBAC), not roles

Status: Accepted · 2026-08-04 · OpenFGA not deployed; the relation model is implemented directly, see Implementation

## Context

The sentence the authorization system has to be able to express is:

> Papa can see live location, only during an active journey, only until
> 12 September, only for safety purposes.

A role cannot say that. Roles carry no subject, no expiry, no purpose and no
incident context. And the difference between this system and stalkerware is
precisely those four dimensions (PRD §10.6, P-008).

## Decision

Authorization is a relation between an accessor, a subject and a scope,
qualified by conditions: expiry, purpose, and whether an incident is active.
The PRD's model (§10.6) is an OpenFGA schema; the semantics it encodes are what
matters and they are implemented in full:

- **Expiry is mandatory.** `consent_grant.expires_at` is `NOT NULL`. There is no
  permanent grant.
- **Purpose binds.** A grant for `safety` does not satisfy a check for
  `routine`, even though the bytes returned would be identical.
- **`incident_only` grants are inert** outside an incident — the lever that lets
  someone say "you may see me only when something is wrong".
- **Guardian-of-minor is an exemption, not a bypass.** It covers `safety` and
  `care` only, and the read is logged and surfaced exactly like any other.
- **Self-access is always allowed** and is still logged.

## Alternatives

**Role-based access control** — rejected. RBAC would make "guardian" mean
"can see everything, forever", which is the exact shape of every family-safety
product that has been used as stalkerware.

## Consequences

- Every read of another member's data goes through a decision that writes an
  access-log row, and `Check` **fails closed** if that write fails: an unlogged
  read does not happen. That is a hard availability coupling on the consent
  store, chosen on purpose — an unlogged read is the one thing this module
  exists to prevent.
- The access log is worthless unless somebody sees it, so surfacing it to the
  subject is a background job with its own health signal (backlog size, oldest
  unsurfaced, stalled). A grant ledger nobody reads is theatre.
- OpenFGA is **not** deployed. The relation model lives in
  `backend/internal/consent/consent.go` as Go, which means: no OpenFGA tooling,
  no model-level tests, and every new scope or condition is a code change and a
  deploy rather than a schema edit. The decision matrix in `decide()` is
  hand-maintained and it is the highest-consequence 100 lines in the control
  plane.
- Denials must explain themselves or people route around the system. `decide()`
  keeps the best *near miss* so it can say "your grant covers `care`, not
  `routine`, and it expires on the 12th" rather than a bare 403.

## Implementation

- `backend/internal/consent/consent.go` — `decide()`, `Check()`,
  `recordAccess()`, `RunSurfacing()`, `Health()`
- `backend/internal/store/store.go` — `Grant`, `Access` rows
- `mobile/src/core/types.ts` — `ConsentGrant` with `purpose` and `expiresAt`,
  `AccessLogEntry`
- `mobile/app/(tabs)/consent.tsx` — the ledger as the family sees it
- `mobile/src/net/api.ts` — `KV-2001` grant expired, `KV-2002` purpose mismatch
- PRD §10.6 — the OpenFGA schema this implements
