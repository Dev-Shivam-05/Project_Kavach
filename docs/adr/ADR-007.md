# ADR-007 — NATS JetStream as the message bus, not Kafka

Status: Accepted · 2026-08-04 · realised as an in-process file-backed bus, see Implementation

## Context

`sos-ingest` fsyncs an incident and must hand it to the control plane, the
realtime gateway and the canary without waiting for any of them (docs/02
§2.5.1). That is a durable, replayable, at-least-once stream with per-family
subjects. The candidate brokers differ by two orders of magnitude in operational
weight (PRD §4.5).

## Decision

NATS JetStream. Subjects namespaced `fam.{id}.*` (PRD §15.4), a durable stream,
per-consumer cursors that survive restart, at-least-once delivery, consumers
deduplicating on `(incident_id, hlc)`. Its built-in KV store also removes any
need for Redis.

## Alternatives

- **Kafka** — rejected. A 1 GB JVM heap and a partition-rebalance model for a
  family of eight is absurd, and the operational surface is a second full-time
  skill.
- **RabbitMQ** — rejected. Weaker replay story for what is fundamentally a log.
- **Redis Streams** — rejected. Durability semantics that need care to get right
  for the one message that must not be lost.

## Consequences

- The stdlib-only constraint (ADR-003) takes the reasoning one step further than
  the PRD did: at family scale the broker is a *directory*, not a daemon.
  `backend/internal/bus/bus.go` implements the JetStream semantics the
  architecture relies on, against a file.
- ⚠ **This clause said "the broker and its only publisher live in the same
  process" and was quietly load-bearing for a year.** It was not a design
  choice, it was a description of a limitation nobody had noticed: `internal/bus`
  could not deliver across a process at all, so the four-container deployment
  this ADR's Implementation section describes was four programs that each worked
  alone (D-027, RISK 17, 20 Aug). Closed the same day — `stream.wal` is opened
  `O_APPEND` and readers tail it — but the sentence is left here rather than
  edited away, because the failure was that a true-sounding sentence went
  unchecked, not that it was badly worded.
- What that costs, stated plainly: **one host**. Cross-*process* works; there is
  still no broker to which a second *machine* could subscribe, so horizontal
  scale-out is not available without doing the NATS migration. The bus is a
  directory, and every consumer must be pointed at the same one —
  `ops/README.md` documents the failure where two processes replay two different
  `stream.wal` files and silently disagree.
- **Multi-writer is now a property of the file format, so treat it as one.** One
  whole record per `Write` on an `O_APPEND` handle is what makes concurrent
  appends safe; a record split across two `Write` calls, or placed with
  `WriteAt`, reopens D-027 with every in-process test still passing. `Seq` is
  the record's ordinal in the file for the same reason a NATS stream sequence is
  the server's and not the client's.
- Delivery is a **250 ms poll**, not a push. That poll interval is a floor
  underneath the t3 clock. It is well inside the NFR-002 budget, and it is still
  latency the real broker would not have added.
- The gain is structural and worth keeping through any future migration:
  `PublishEphemeral` delivers only to ephemeral subscribers and is never written
  to the stream file, and `Publish` **rejects** `KindLocationPrecise`. Class A′
  ("consumed in memory, never persisted", docs/02 §2.4.6) is enforced by which
  list a subscriber is on, not by a comment somebody could ignore.

## Implementation

- `backend/internal/bus/bus.go` — subjects, durable stream, cursors,
  `PublishEphemeral`, the Class A′ rejection in `Publish`, and `poll()`, which
  is the only thing that reads what another process wrote
- `backend/internal/wal/wal.go` — the append-only file underneath it. Two modes:
  `Open` for a single writer (`sos.wal`, ADR-002, untouched) and `OpenShared`
  for the bus, where the kernel places records with `O_APPEND` and `Tail`
  re-stats the file
- `ops/docker-compose.yml` — `KAVACH_BUS_DIR` set explicitly on all four
  services, because the per-binary defaults are relative and disagree
- `ops/README.md` §2 — the on-disk layout, and the bus as "the seam"
- `ops/e2e-two-binaries.sh` — the seam exercised by two real binaries: an SOS
  posted to `sos-ingest` climbing the ladder in `control-plane`
