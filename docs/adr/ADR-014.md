# ADR-014 — Escalation timers are durable rows claimed with `FOR UPDATE SKIP LOCKED`, polled at 250 ms

Status: Accepted · 2026-08-04

## Context

The ladder is a sequence of deadlines: the cancel window expires at t+20 s, L1
repeats at t+30 s, SMS joins at t+60 s, L2 at t+90 s. Each deadline must fire
exactly once, and the process holding it **will** die — during a deploy, during
an OOM, during a host reboot at 3 a.m. while somebody's incident sits at
ACTIVE_L1 waiting for the 90-second rung (PRD §4.5, docs/02 §2.5.4).

## Decision

Every timer is a durable row. A worker claims it by moving it from pending to
claimed in one atomic operation — `SELECT … FOR UPDATE SKIP LOCKED` in
Postgres — executes it, and the claim is what makes execution at-most-once.
N stateless workers compete for the same table; there is no leader election
because `SKIP LOCKED` is what leader election would have been for (F-13).

Polling is adaptive: **250 ms** when a timer is due within 5 s, 2 s otherwise.
Identical latency where it matters, far less work where it does not.

★ Do not use `time.AfterFunc`. Do not use cron.

## Alternatives

- **In-memory timers** — rejected. They die with the process, silently, and the
  incident they were holding stalls with no error anywhere.
- **Cron** — rejected. Minute granularity against a ladder measured in seconds.
- **An external scheduler** — rejected. A second system to run, and a second
  system whose outage is invisible until a rung does not fire.

## Consequences

- The escalation ladder is only as available as the store. If the store cannot
  be written, no timer fires — the failure is loud rather than silent, which is
  the trade being made, but it is still a hard dependency.
- Polling means a floor on precision: a timer can fire up to one poll interval
  late. 250 ms against rungs measured in tens of seconds is acceptable; the
  arithmetic should be redone before anyone shortens a rung.
- N competing workers means every timer handler must be idempotent. The claim
  makes execution at-most-once, not exactly-once: a worker that dies after
  claiming and before executing loses that firing.
- The compensating benefit is the one that matters at 3 a.m.: **the pending
  ladder is a table you can read.** `KAVACH_ESCALATION_WORKERS` is a throughput
  knob and nothing else, and adding a worker requires no coordination.
- The file-backed store has no transactional claim, so the engine falls back to
  `claimOptimistic` behind a mutex. That is correct in one process and **not**
  correct across processes — a second control-plane instance against the same
  data directory could double-fire. Real `SKIP LOCKED` arrives with ADR-006.

## Implementation

- `backend/internal/escalation/engine.go` — `TimerClaimer`, `claim()`,
  `claimOptimistic()`, `PollFast = 250ms`, the action constants
- `backend/internal/store/store.go` — `Timer` rows
- `backend/cmd/control-plane/main.go` — `KAVACH_ESCALATION_WORKERS`
- `ops/docker-compose.yml` — workers set to 3, with F-13 noted inline
