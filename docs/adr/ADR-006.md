# ADR-006 — PostgreSQL + PostGIS + TimescaleDB is the only datastore

Status: Accepted · 2026-08-04 · **not yet deployed** — see Implementation

## Context

The data here has four shapes: relational (families, devices, grants), spatial
(coarse cells, neighbour matching), time-series (location points, heartbeats,
delivery attempts) and full-text (incident notes, after-action reports). The
reflex is a datastore per shape. At this scale that means four backup
procedures, four restore drills and four sets of operational knowledge for one
person to hold (PRD §4.5, §8).

## Decision

One datastore. PostgreSQL with the PostGIS and TimescaleDB extensions covers all
four shapes, and Postgres full-text search removes any argument for
Elasticsearch. Row-level security carries family isolation (PRD §8.1); a trigger
makes `incident_event` immutable (ADR-012).

## Alternatives

- **Polyglot persistence** — rejected. One restore drill you actually run beats
  four you plan to.
- **MongoDB** — rejected. Nothing here wants a document model, and the
  relational integrity between family, member, grant and incident is the part
  that must not be wrong.

## Consequences

- Postgres becomes a single point of failure for the whole non-critical tier.
  That is survivable only because `sos-ingest` never reads it (ADR-002).
- Extensions are an upgrade constraint: a major-version Postgres bump now has to
  wait for PostGIS and TimescaleDB to be available for it.
- **This deployment does not run Postgres.** The delivery constraint was "no
  Docker, no external modules" (ADR-003), so `backend/internal/store/store.go`
  stands in. It is a deliberate stand-in, not a toy — it keeps the table names,
  the column names and the semantics from docs/02 §2.8 — but it is honestly
  weaker in ways that matter:
  - no row-level security; family isolation is a `family_id` validated on write
    in application code
  - no PostGIS; there is no spatial index and no radius query
  - single writer under an `RWMutex`, whole-table atomic rewrite per commit
  - the append-only rule is `ErrAppendOnly` returned by the mutating methods
    rather than a database trigger that cannot be bypassed
- The migration to real Postgres is therefore outstanding work, and the schema
  compatibility above is what keeps it a port rather than a redesign. The
  on-device SQLite schema uses snake_case column names for the same reason
  (`mobile/src/db/schema.ts`).

## Implementation

- `backend/internal/store/store.go` — the stand-in, with the §2.8 semantics it
  preserves listed in its package comment
- `mobile/src/db/schema.ts` — the on-device mirror, named one-for-one with the
  server schema
- `docs/02-System-Architecture.md` §2.8 — the schema this is a port of
- PRD §8.1 — the RLS policies that have no equivalent here yet
