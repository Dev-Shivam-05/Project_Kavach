# ADR-012 — An append-only event log for incidents; no CRDT library

Status: Accepted · 2026-08-04

## Context

Two phones and a server all hold a view of the same incident, and they go out of
sync constantly: the subject's phone is offline, an SMS arrives before the HTTP
envelope it duplicates (F-09), a BLE relay delivers an event through a third
device (docs/02 §2.10.3). Something has to merge those views without a human
adjudicating, and without ever losing an event (PRD §4.5, §11).

## Decision

Incidents are an **append-only log of events**, ordered by Hybrid Logical Clock,
merged by set union. Conflict-free by construction: two devices that saw
different events converge by taking both, and an event that arrives twice is
deduplicated on `(incident_id, hlc)`.

The device is the source of truth; the server is a replica and a relay (docs/02
§2.10.4). Every operation executes locally first, appends to the local log, then
syncs — which is why the app is fully usable at L0 with no backend at all.

A CRDT library is reserved for the one case that genuinely needs it: concurrent
text editing in shared notes. Not incidents.

## Alternatives

**Automerge / Yjs everywhere** — rejected. A general CRDT library brings a
document model, a merge algorithm and a wire format to solve a problem that set
union already solves for a log that is only ever appended to.

## Consequences

- **Nothing can be deleted.** A wrong event — a mis-tapped trigger, a bad
  location, a duplicated relay — is permanent and can only be superseded by a
  later event. That is the correct property for an accountability record and it
  is a real cost for a family that would like an embarrassing incident gone.
  Retention for incident events is *forever*, and deletion requires a 2-of-3
  quorum (PRD §8.3).
- The log only grows. On-device storage grows monotonically with incident count.
  At family scale this is not a problem; the property is worth naming anyway.
- The on-device schema has **no foreign keys**, deliberately. Sync delivers an
  `incident_event` before its `incident` more often than expected, and a foreign
  key would turn a benign out-of-order arrival into a dropped emergency event.
  Referential integrity is the server's job; survivability is the schema's.
- Immutability has to be enforced where the writes happen, or it decays. The
  server-side rule is a Postgres trigger in the target schema (§2.8.4) and
  `ErrAppendOnly` from the store's mutating methods today (ADR-006).
- HLC is 48-bit physical + 16-bit logical + 32-bit node. The PRD called it 12
  bytes with a 48-bit node id, which does not fit; the node id was narrowed
  rather than the buffer widened (DELIVERY.md §5).
