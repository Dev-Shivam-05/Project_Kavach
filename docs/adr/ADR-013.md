# ADR-013 — The escalation policy is server-authoritative, versioned, and devices never write it

Status: Accepted · 2026-08-04

## Context

The escalation policy decides how long the cancel window is, who is woken at
each rung, when SMS joins, and whether audio starts. Two devices holding
different answers to those questions is not a merge conflict — it is two
responders driving to different places under different rules, and an after-action
report that cannot explain what happened (PRD §4.5, §7.5).

Most of this system is deliberately last-write-wins or set-union (ADR-012).
This is the part that must be totally ordered.

## Decision

The policy is **data, not code**: a versioned document the server owns. Devices
cache it locally so T0 escalates correctly with no network, and devices never
write it. Every incident and every state transition is stamped with
`policy_version`, so an after-action report for a six-month-old incident renders
under the rules that were in force at the time (P-069).

Where the policy and a local heuristic both have an opinion — a risk-context
modulation of the cancel window, for example — **policy wins**.

## Alternatives

**Offline-editable policy** — rejected. It is the natural thing to build in an
offline-first system, and it produces the one class of divergence that cannot be
reconciled after the fact.

## Consequences

- A family cannot change their own cancel window while offline. The edit has to
  reach the server and come back as a new version. For a system whose entire
  design premise is that the network is unreliable, that is a genuine
  inconsistency, and it is accepted here specifically because the alternative is
  unrecoverable.
- A device that has not synced escalates under a **stale but internally
  consistent** policy. That is correct by design, and it means a policy change
  made today does not necessarily apply to a phone that has been offline for a
  week. The version stamp is what makes that legible afterwards instead of
  mysterious.
- Every incident record carries a version number that must be resolvable
  forever, so policy versions can never be deleted — a small permanent storage
  obligation in exchange for explicable history.
- The default policy is compiled into the client (`DEFAULT_POLICY`,
  `DEFAULT_POLICY_VERSION = 1`) so a phone that has never synced still has a
  complete, coherent ladder. That default is itself a policy version and must be
  bumped like any other.

## Implementation

- `mobile/src/core/policy.ts` — the policy as data, per-scenario table from
  PRD §7.5, `DEFAULT_POLICY_VERSION`
- `mobile/src/db/schema.ts` — `policy_cache`, so T0 escalates with no network
- `mobile/src/db/repos.ts` — the cache is read-through, never written by the
  device
- `mobile/src/net/api.ts` — policy fetch, server-authoritative
- `mobile/src/t0/triggerRouter.ts` — where policy and local timing meet; policy
  wins
- `mobile/src/domain/riskContext.ts` — modulation that stays inside the policy's
  bounds
- `backend/internal/escalation/engine.go` — the server-side ladder that the
  version describes
