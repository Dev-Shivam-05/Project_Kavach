# ADR-005 — Docker Compose, not Kubernetes

Status: Accepted · 2026-08-04

## Context

Four processes, one host, one operator who is also the developer and who will be
doing this at 3 a.m. with a phone in one hand (PRD §4.5, §13).

## Decision

`ops/docker-compose.yml` is the deployment. Four services, one named volume,
`restart: unless-stopped`, healthchecks on each. `ops/run-backend.ps1` is the
no-Docker path for a machine that has only a Go toolchain.

## Alternatives

- **Kubernetes** — rejected. A control plane to maintain, a networking model to
  debug and a quarterly upgrade treadmill, in exchange for orchestration
  features that four processes on one host never use.
- **k3s / Nomad** — rejected for now on the same reasoning. k3s is a two-day
  migration if the estate ever grows enough to need it, so this decision is
  cheap to reverse.

## Consequences

- No rolling deploys, no automatic rescheduling, no multi-host failover. If the
  host dies, the backend is down until someone brings it back. The architecture
  absorbs this — the client's L0 floor works with no backend at all (PRD §4.4)
  and `sos-ingest` is the only thing whose downtime is serious.
- Blue-green is manual. The control plane cooperates (`SIGTERM` flips `/readyz`
  and drains for `KAVACH_DRAIN` before the listener closes), but the traffic
  switch is a human with a proxy config.
- The two run paths can drift. They already have: `ops/README.md` documents that
  `run-backend.ps1`'s start path passes flags `realtime-gw` and `canary` do not
  define, so both exit immediately. Documented rather than hidden, and the env
  vars are deliberately identical across both paths so the *configuration*
  cannot drift even while the scripts do.

## Implementation

- `ops/docker-compose.yml` — four services; `sos-ingest` has its own build and
  no `depends_on` (ADR-002)
- `ops/run-backend.ps1` — build and stop paths; start path has a known gap
- `ops/README.md` §1, §5 — both paths and the full environment-variable table
