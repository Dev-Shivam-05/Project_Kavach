# ADR-021 — Ship GroupBox now, migrate to MLS in Phase 2, behind a scheme byte

Status: Accepted · 2026-08-04 · defers ADR-008 in time, does not reverse it · **review at the Phase 2 gate**

## Context

ADR-008 chose MLS, correctly. The PRD then scheduled it at 21 days on the
Phase 0 critical path. Realistically it is 8–14 weeks including the Delivery
Service, epoch recovery and key transparency — and that single line item is the
most likely cause of never reaching the Phase 1 gate, which is the twelve weeks
that carry ~90% of the life-saving value (finding F-08, docs/02 §2.4.1).

The threat that E2EE exists to answer here is **T3: the server**. That is what
must be closed from week one.

## Decision

Phase 1 ships **GroupBox** (`0x01`):

| | GroupBox (Phase 1) | MLS (Phase 2) |
|---|---|---|
| Group key | per-family static X25519, generated on the founding device | TreeKEM epoch secrets |
| Distribution | sealed to each enrolled device's identity public key at enrolment | Welcome messages |
| Content | XChaCha20-Poly1305, keys HKDF'd from the group key + context | HKDF from the exporter secret |
| Server sees | **ciphertext only** | ciphertext only |
| Forward secrecy | ❌ | ✅ |
| Post-compromise security | ❌ | ✅ |
| Effort | ~3 days | 8–14 weeks |

Every `sealed_payload` carries a **1-byte scheme discriminator**, so the
migration is additive: devices negotiate the highest scheme both sides support
and old clients keep working (NFR-016, P-060). `SCHEME_MLS = 0x02` is reserved
in the code today.

**The dated commitment.** MLS is the Phase 2 workstream in
`docs/03-Implementation-Guide.md` §3.5 — weeks 17–30. If Phase 2 closes with
`SCHEME_MLS` still unused, that is a failure to record here and to raise at the
gate, not a schedule to renegotiate quietly. "We'll do MLS later" becoming "we
never did MLS" is the specific outcome this paragraph exists to prevent.

## Alternatives

- **MLS on the Phase 1 critical path** — rejected on schedule risk, not on
  merit. It remains the destination (ADR-008).
- **No E2EE until MLS lands** — rejected. It would leave T3 open for months and
  make the server the richest target in the family's life during the exact
  period when the system is least mature.
- **A bespoke group scheme** — rejected. GroupBox is not novel cryptography: it
  is a sealed box and an AEAD, both standard constructions used the way their
  designers intended.

## Consequences

- **No forward secrecy.** An attacker who obtains the family group secret can
  decrypt every message ever sealed under it, including ones captured months
  earlier.
- **No post-compromise security.** Recovery from a compromised device is not
  automatic. The group secret does not rotate on its own, so a compromise
  persists until the family generates a new secret and re-enrols every device by
  hand. Under MLS that is a Commit; here it is a manual procedure that nobody
  will perform unless they know they were compromised.
- Both of those address **threat T6, a compromised family device**, rated
  LOW × HIGH. That rating is what makes this trade acceptable and it is the
  first thing to re-examine if the rating changes.
- One static secret means blast radius does not decay with time. The longer the
  family runs on `0x01`, the more history a single compromise exposes — which is
  the real reason the Phase 2 commitment above has a deadline rather than an
  aspiration.
- The scheme byte is only useful if it is honoured on the read path from the
  start. A Phase 1 client that ignores it and assumes GroupBox will break on the
  first `0x02` ciphertext it meets.
- What is bought: NFR-013 and invariant I-3 are satisfied from week one — the
  server holds ciphertext for precise location, health, audio, documents and
  camera frames — for three days of work instead of three months.

## Implementation

- `mobile/src/crypto/index.ts` — `SCHEME_GROUPBOX = 0x01`, `SCHEME_MLS = 0x02`,
  the sealed-box distribution, HKDF-derived scope keys, XChaCha20-Poly1305
- `mobile/src/t0/blackbox.ts` — the Family Group Secret gates sealing the window
- `mobile/src/state/nodeStore.ts` — camera snapshots *and* their index are
  sealed; no key means the node refuses to arm
- `mobile/app/vault.tsx` — the vault key is **independent** of the group secret
  and Shamir-split 2-of-3, because it must survive total device loss
- `mobile/test/invariants.test.ts` — I-3 / T3: the server sees ciphertext
- `docs/02-System-Architecture.md` §2.4.1 — the phasing table
- `docs/03-Implementation-Guide.md` §3.5 — the Phase 2 migration workstream
