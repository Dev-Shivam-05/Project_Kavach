# ADR-004 — A modular monolith, not microservices

Status: Accepted · 2026-08-04 · bounded by ADR-002, which splits out the one service that must be independent

## Context

Eight users. One part-time developer (PRD §1.7 C4). Microservices at that scale
spend most of the effort on the plumbing between services — service discovery,
tracing, retry semantics, deploy ordering — for decoupling nobody is there to
benefit from (PRD §4.5).

## Decision

The control plane is one binary composed of packages with enforced boundaries.
Each package owns its data and exposes a Go API; dependencies flow downward only
(docs/02 §2.1, R6). The seams are real — `escalation` cannot reach into
`consent`'s state, it calls it — so extracting a service later is a build change,
not a rewrite.

`sos-ingest` is the exception, and it is carved out for a criticality reason
(ADR-002), not a scaling one.

## Alternatives

- **Microservices** — rejected. PRD §4.5 puts the plumbing at roughly 60% of the
  total effort for this user count.
- **Serverless** — rejected. Cold starts on a path measured in the low hundreds
  of milliseconds, and a per-invocation billing model for a service that must
  hold a WAL and durable timers.

## Consequences

- One deploy for everything non-critical. A bug in the drill scorecard takes the
  consent ledger down with it. That is accepted because the whole tier is
  explicitly "allowed to be down" — but it is a real coupling and it will
  eventually cause an outage that a service split would have contained.
- The module boundaries are conventions enforced by review and by import
  direction, not by a network. Nothing stops a future edit from reaching across
  a seam; the only guard is that Go's import cycle rules make the worst
  violations impossible.
- Scaling is vertical only. At family scale that is not a constraint; if this
  ever served more than one family it would become one.

## Implementation

- `backend/cmd/control-plane/main.go` — composition root; wires the packages,
  owns the HTTP surface
- `backend/internal/store` — the durable record; every other package takes it as
  a dependency, none of them bypass it
- `backend/internal/escalation` — the ladder, depends on `store`, `notify`,
  `incident`
- `backend/internal/consent` — grants, checks, access log surfacing
- `backend/internal/notify` — channel orchestration and delivery rows
- `backend/internal/incident/machine_gen.go` — generated from
  `spec/state-machine.yaml`; both the Go and TypeScript machines come from it
