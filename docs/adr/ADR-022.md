# ADR-022 — The signature algorithm is a property of the key, and the verifier ships first

Status: Accepted · 2026-08-04 · partially realised — the verifier is live, the device still signs Ed25519

## Context

The emergency signing key proves an SOS came from a particular phone. Until now
it was generated by `@noble/curves` in `mobile/src/crypto/index.ts` and kept as
bytes in the JavaScript heap for the whole life of the process. Any code running
in that runtime — including anything that arrives through a compromised
dependency — can read it. That is not a theoretical weakness; it is the one key
in the system whose disclosure lets somebody forge another person's emergency.

The fix is a key the runtime cannot read, held by AndroidKeyStore. And there the
platform imposes a constraint that decides the rest of this ADR:

**Android Keystore gained Curve25519 at API 33.** Kavach ships to API 26, onto
mid-range Android phones sold in India — exactly the devices that do not have
it. So a hardware-held key on the fleet we actually serve is EC P-256 signed
`SHA256withECDSA`, not Ed25519.

There is no version of this where one algorithm covers the fleet. Ed25519
everywhere means the key stays in the heap on every phone. P-256 everywhere
means no key at all on Expo Go, on iOS, and on any device whose keystore
refuses.

## Decision

**One family holds both kinds of key at once, and the verifier decides which is
which by looking at the key it has on file — never at anything the sender said.**

- `mobile/src/crypto/hardware.ts` resolves, per key role, to the strongest
  backing actually obtained, and reports which in those words: `strongbox`,
  `tee`, `keystore_software`, `js_heap`. A software key reported as hardware is
  the precise lie P-031 exists to prevent, so every fallback carries the reason
  it happened and `app/diagnostics.tsx` renders it verbatim.
- `envelope.ParseVerifyingKey` dispatches on the **encoding**: 32 raw bytes is
  Ed25519, X.509 SubjectPublicKeyInfo carrying a P-256 point is ECDSA. The
  smallest possible P-256 SPKI is 91 bytes, so the length test is unambiguous.
- The curve is **pinned to P-256**. A P-384 or P-521 SPKI parses fine and would
  verify fine; accepting one would mean the fleet quietly runs an algorithm no
  device was provisioned with and no test covers.
- **`sos-ingest` never reads an algorithm field off the request.** A
  self-declared algorithm is an attacker-controlled downgrade. There is no
  reason to accept one when the key encoding already answers the question.

### ★ The verifier ships before the signer ★

This is the operational half of the decision and it is not optional.

Deployed in this order, a phone that starts emitting P-256 meets a server that
already understands it. Deployed in the other order, ADR-018 does exactly what
it is designed to do: every real emergency from an upgraded phone is **accepted
and flagged `UNVERIFIED`**. Nothing errors. Nothing pages. Signature
verification is simply gone across the upgraded fleet, and the first person to
notice is whoever audits the flag rate.

So this ADR lands in two parts, and the second one waits:

| | Status |
|---|---|
| `envelope.VerifyingKey` — parses both, verifies both, refuses each other's signatures | **shipped** |
| `sos-ingest` key cache typed `VerifyingKey`, parsed at load | **shipped** |
| `KeyVault.kt` — the AndroidKeyStore key itself | **shipped, uncompiled** — needs an EAS build; there is no JDK on the dev machine |
| `prepareKeys()` at bootstrap, backing rendered in diagnostics | **shipped** |
| `buildSignedEnvelope()` signing through `signWithEmergencyKey()` | **not shipped — see below** |

## What blocks the last row, and why it is not a small change

`buildEnvelope()` in `mobile/src/t0/triggerRouter.ts` is **synchronous**, and
deliberately so. The header at `triggerRouter.ts:684` states the constraint:
nothing on the trigger path may await a network, a GNSS fix or a disk flush. An
envelope must exist the instant the button is pressed.

Signing through AndroidKeyStore is a native bridge call, and native bridge calls
are asynchronous. So adopting the hardware signature is not a matter of swapping
one function for another — it changes when, on the SOS path, the envelope
becomes signed. The two candidate shapes both have real costs:

1. **Build sync, upgrade the signature in the dispatcher before first
   transmission.** Keeps the synchronous guarantee. Costs: two signatures exist
   transiently for one incident, and the upgrade must not delay the first
   transport.
2. **Pre-sign a nonce at boot and bind it.** Keeps signing off the trigger path
   entirely. Costs: a genuinely new protocol construction, and new failure modes
   at exactly the wrong moment.

Choosing between those on the most safety-critical path in the product, in the
same change that introduces the algorithm, is how a safety product breaks. It
gets its own ADR and its own device testing.

## Consequences

- **Both algorithms must be supported by every verifier, forever.** A device
  changes kind across a reinstall onto newer hardware, so a family is a mixed
  fleet indefinitely. There is no migration that ends.
- **`Seal()` still signs Ed25519.** The relay and SMS-synthesis paths sign on the
  server with a server-held key; nothing about them wants a device keystore.
- **The Android JCA agreement is assumed, not yet proven.** Go's `crypto/ecdsa`
  and Android's `SHA256withECDSA` are both specified to produce an ASN.1 DER
  SEQUENCE of `r` and `s` over a SHA-256 digest, and `verifykey_test.go` pins the
  Go side. The cross-language half is only real once a phone with a keystore
  signs and this code accepts it — the same gap `crosslang_test.go` closed for
  Ed25519, still open for P-256.
- **`js_heap` is rendered in red**, not in grey. It is the common case in Expo
  Go, and naming it as a weakness is the point.

## Alternatives

**Ed25519 in software everywhere; no hardware key at all.** The status quo.
Rejected: it leaves the one key whose disclosure permits forging another
person's emergency readable by anything in the JS runtime.

**Require API 33 for hardware keys and let older phones go without.** Rejected on
the same ground the whole product is built on: the phones that would go without
are the phones the product exists for.

**Carry the algorithm in the envelope so the server can dispatch on it.**
Rejected. It is an attacker-controlled field on an endpoint that takes no bearer
token (P-007), it invites a downgrade, and it is unnecessary — the key encoding
already carries the answer.

**Wrap the P-256 signature so it looks like Ed25519 to old servers.** Rejected as
incoherent: the bytes verify or they do not.
