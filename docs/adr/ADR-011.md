# ADR-011 — One cross-platform client over native T0 modules; the client framework is React Native (Expo)

Status: Accepted · 2026-08-04 · supersedes the "Flutter" row in PRD §4.5 on the framework; the T0 half is unchanged

## Context

The client has two halves with opposite requirements. T0 must be native, must
survive the app being killed, and must not depend on any managed runtime
(ADR-001). T1/T2 — screens, maps, consent, journeys, timeline — is ordinary
application work where the cost is developer hours and the risk is that a
part-time developer maintains two of everything.

The PRD calls this "the least important decision here", and it is right: the
native modules matter ten times more than the framework.

## Decision

One cross-platform framework for T1/T2 sitting on native modules for T0.

The framework is **React Native under Expo (SDK 57)**, not Flutter. Three of the
PRD's reasons for Flutter no longer decide anything:

- The OpenMLS Dart binding was a genuine advantage — and ADR-021 replaced MLS
  with GroupBox for Phase 1, implemented in TypeScript over `@noble/*`. There is
  no Dart binding to prefer.
- "One rendering engine so the panic UI is pixel-identical everywhere" assumed
  two platforms. ADR-015 puts the entire T0 plane on Android, so the second
  platform is a reduced client, not a second panic UI.
- `expo-modules` gives the Kotlin T0 module a first-class native boundary
  (`mobile/modules/kavach-t0/expo-module.config.json`), which was the capability
  the framework actually had to provide.

The half of the decision that carries weight is unchanged: **T0 is native Kotlin
and owns the trigger path**; the framework is a consumer of it and can never
gate it.

## Alternatives

- **Flutter** — the PRD's choice, superseded above. Not a wrong answer; a
  differently-weighted one once MLS moved out of Phase 1.
- **Kotlin Multiplatform** — rejected. Shares logic, not UI; the UI is most of
  the work here.
- **Fully native ×2** — rejected. Two complete applications for one part-time
  developer.

## Consequences

- Cross-platform T0 is roughly **1.6× the client work** of a single-platform
  build (docs/04 W1): every T0 feature would exist in Kotlin and in Swift with a
  bridge to the shared runtime. This is capped, not paid, by ADR-015 shipping T0
  on Android only — the cost is deferred to whenever an iOS T0 is attempted, and
  it is the reason the PRD says primary safety devices SHOULD be Android.
- The JS runtime is not trustworthy for T0 and is not treated as such. Nothing
  in `mobile/src/t0/` is authoritative when the native module is present; it is
  the degraded mirror for builds where `requireOptionalNativeModule('KavachT0')`
  returns `null`.
- `null` is the dangerous case: in Expo Go the whole native plane is absent and
  the app still runs. The diagnostics screen reports `nativeT0Present: false` as
  a **failing check** rather than counting a composer-based SMS as "sent"
  (P-031, DELIVERY.md §4).
- The JS↔Kotlin boundary is by name, so a rename compiles on both sides and
  fails on a device. `mobile/test/native-bridge.test.ts` pins all 14 function
  names, the module id, `directBootAware` and the two receivers.
- React 19 and Expo SDK 57 move fast. The pin discipline is now load-bearing:
  DELIVERY.md §2 records an EAS build failing on `react-dom` resolving against a
  different `react` patch than the lockfile assumed.

## Implementation

- `mobile/modules/kavach-t0/` — the native plane: `KavachT0Module.kt`,
  `KavachForegroundService.kt`, `BootReceiver.kt`, `ShutdownReceiver.kt`,
  `KavachDeviceAdminReceiver.kt`, `DeviceOwnerConfigurator.kt`
- `mobile/modules/kavach-t0/src/KavachT0.types.ts` — the native type surface, and
  why there is no iOS stub
- `mobile/src/t0/native.ts` — `requireOptionalNativeModule`, and the rule that a
  missing module degrades rather than throws
- `mobile/test/native-bridge.test.ts` — name-drift guard
- `mobile/app/` — expo-router, 19 screens; `mobile/src/ui/` — the design system
- `docs/04-Pros-and-Cons-Analysis.md` W1 — the 1.6× figure
