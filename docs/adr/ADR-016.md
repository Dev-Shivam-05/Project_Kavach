# ADR-016 — Home Assistant is the entire smart-home plane

Status: Accepted · 2026-08-04 · bridge modelled, no live Home Assistant integration yet

## Context

Smoke, gas, water leak, door state, motion. Every one of those is a different
protocol — Zigbee, Z-Wave, Matter, Thread, ESPHome, a dozen vendor clouds — and
each protocol is a moving target with its own certification, its own pairing
model and its own breaking changes (PRD §14.2).

## Decision

Do not build any of it. Home Assistant is the smart-home plane. Kavach speaks to
exactly one thing — the Home Assistant bridge — and Home Assistant speaks to
everything else. Events arrive as `ha_event` rows: an entity, a kind, a
severity, a timestamp and a list of suggested actions.

## Alternatives

**Build Matter/Zigbee support directly** — rejected. 8–12 months of work plus
perpetual protocol maintenance, to arrive at a worse version of software that
already exists and is maintained by hundreds of people.

## Consequences

- **A ₹4,000 Raspberry Pi becomes load-bearing for smoke and gas detection.**
  That sentence should be uncomfortable, because it is the honest description:
  the detector on the ceiling is fine, but the path from that detector to a
  family member's phone runs through one small computer with an SD card, and SD
  cards fail. Mitigations named in the PRD — a UPS and a hot spare — are the
  minimum, and neither is a substitute for the family knowing that this leg of
  the system has a single point of failure in it.
- A dead Pi is silent. Nothing about a smoke sensor that stops reporting looks
  different from a smoke sensor with nothing to report. Heartbeat-gap alerting
  on the bridge is therefore not optional; it is the only thing that
  distinguishes "quiet" from "gone".
- Home Assistant's release cadence becomes ours. A breaking change upstream is a
  breaking change here, on their schedule.
- The scope boundary is worth the cost: the smart-home plane is Phase 4 work
  (PRD §3.7) and this decision is what keeps it from consuming the phases that
  carry the life-saving value.
- **Not yet integrated.** The event model, the schema and the UI exist; the
  bridge is currently exercised through the demo generator, not a live Home
  Assistant instance. Nothing here has been validated against a real smoke
  sensor, and no reader should assume otherwise.

## Implementation

- `mobile/src/db/schema.ts` — the `ha_event` table
- `mobile/src/core/types.ts` — the Home Assistant bridge types
- `mobile/src/domain/demo.ts` — a bridge device in the demo family, which is the
  only place it is exercised today
- `mobile/src/state/nodeStore.ts` — the neighbouring Phase 2 node plane, kept in
  a separate store slice for the same "must not wedge the safety plane" reason
- PRD §14.2 — the integration design
