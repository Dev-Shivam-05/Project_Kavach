# ADR-003 — Go, standard library only, for the entire backend

Status: Accepted · 2026-08-04

## Context

One part-time developer maintaining a safety system for a decade (PRD §1.7 C4).
The question is not which language is best in 2026; it is which toolchain will
still build, still be understood, and still be patched in 2034 by the same
person, part-time (PRD §4.5).

## Decision

Go for all four backend binaries. `backend/go.mod` declares the module and the
Go version and nothing else — **zero `require` lines, no `go.sum`, no vendor
directory**. Everything is the standard library.

The stdlib constraint is a decision on top of the language choice, and it is
what makes the rest of the operational story possible: four static binaries, an
`alpine` runtime layer with nothing in it to patch, and a supply chain with no
third parties in it.

## Alternatives

- **Node/TypeScript** — rejected. Velocity is real, but it would mean sharing a
  language with the client at the price of a dependency tree that needs
  attention every month.
- **Elixir** — rejected, and it is arguably the better technical fit: OTP
  supervision and Phoenix Presence map onto this problem almost exactly. Rejected
  on maintainer economics, not on merit.
- **Rust** — rejected. The safety argument does not pay for the compile-time and
  cognitive cost at this scale.

## Consequences

- Things that would have been one import are now source in this repository:
  the RFC 6455 WebSocket handshake and frame codec (`backend/cmd/realtime-gw`),
  the pub/sub bus (`internal/bus`), the durable store (`internal/store`), the
  write-ahead log (`internal/wal`). Each is code we own and must debug.
- No ORM, no migration framework, no metrics library. `internal/logx` is a thin
  wrapper over `log/slog` because that is what exists.
- Every hand-rolled substitute is a correctness risk that a library would have
  absorbed. The mitigation is that each is small and directly tested — but
  "small and tested" is weaker than "battle-hardened by thousands of users", and
  pretending otherwise would be dishonest.
- The upside is measurable and not theoretical: `go build ./...` needs nothing
  from the network, the Docker builder is pinned to one image
  (`golang:1.26-alpine`), and there is no dependency-update treadmill at all.

## Implementation

- `backend/go.mod` — `module github.com/kavach/backend`, `go 1.26`, nothing else
- `backend/cmd/{sos-ingest,control-plane,realtime-gw,canary}/main.go`
- `backend/internal/{bus,consent,envelope,escalation,incident,logx,notify,store,wal}`
- `ops/docker-compose.yml` — `CGO_ENABLED=0`, no `go mod download` step anywhere
